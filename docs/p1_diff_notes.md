## 1. 문서 경계와 읽는 법

이 문서는 Diff 담당자가 로직을 통제하며 AI에 구현을 맡기기 위한 정리다. 공용 요구사항·인터페이스·테스트를 변경하거나 대체하지 않는다.

내용의 출처를 다음처럼 구분한다.

- **[공용 계약]** 기존 공용 문서 또는 코드에 명시된 내용. 이 문서에서 새로 합의했다는 뜻이 아니다.
- **[찬의 방향]** 이번 대화에서 찬이 명시한 판단. 팀 전체에 승인된 것으로 취급하지 않는다.
- **[AI 해석·제안]** 방향을 구체화한 설명 또는 해결안. 승인된 구현 기준이 아니다.
- **[미확정]** 구체적인 규칙이나 팀 간 계약 확인이 필요한 부분. AI가 임의로 채우지 않는다.

공용 문서와 차이가 있으면 차이를 유지해서 표시한다. 특히 공용 테스트의 기대 결과를 이 문서에 맞춰 변경하지 않는다.

## 용어집 — 이후 논의의 기준

이 용어집은 기존 공용 타입·설명과 이번 대화의 용어를 정리한다. 새 노드 대응 정책이나 팀 합의를 추가하지 않는다.

| 용어 | 이 문서에서의 의미 |
| --- | --- |
| HTML 태그 | `<p>`, `<li>` 같은 HTML 표기. VDOM 객체나 실제 DOM 객체 자체를 뜻하지 않는다. |
| 실제 DOM | 브라우저 화면을 구성하는 `Element`·`Text` 등의 실제 객체. Diff가 직접 수정하지 않는다. |
| VDOM | 실제 DOM을 비교하기 위한 데이터 트리. `VRoot`와 그 아래 `VNode`로 구성된다. |
| 노드 / VNode | Diff 논의에서 별도 수식 없이 말하는 노드는 VDOM의 `VNode` 객체다. 실제 DOM 노드와 구분한다. |
| 요소 VNode | `nodeType: 1`인 VNode. `tagName`, `attributes`, `properties`, `childNodes` 등을 가진다. |
| 텍스트 VNode | `nodeType: 3`인 VNode. 문자열은 `nodeValue`에 있고 `childNodes`는 빈 배열이다. |
| 루트 / VRoot | 실제 영역 컨테이너에 대응하는 논리적 루트. `childNodes`와 `dom`만 가지며, 컨테이너 자체의 태그·속성은 비교하지 않는다. |
| 태그 이름 / tagName | 요소 종류를 나타내는 VNode 필드. 예: `'LI'`, `'P'`. 텍스트 VNode에서는 `null`이다. |
| 필드 / 객체 프로퍼티 | 자바스크립트 객체에서 `객체.이름`으로 접근하는 항목. 이 문서에서는 혼동을 피하려고 **필드**라고 부른다. 예: `vnode.tagName`, `vnode.nodeValue`, `vnode.attributes`. |
| HTML 속성 / attribute | HTML에 명시된 이름·값. 이 문서에서는 **HTML 속성**이라고 부른다. VNode의 `attributes` 필드에 `{ name, value }`로 저장한다. |
| 노드 식별자 / 이 프로젝트의 key | 이름이 `key`인 HTML 속성의 값을 노드 식별자로 사용한다. 예: `<li key="a">`의 `'a'`. VNode에서는 `attributes` 중 `name === 'key'`인 항목의 `value`를 읽는다. 일반적인 자바스크립트 객체의 프로퍼티 키와 구분한다. |
| key가 있는 요소 | 이름이 `key`인 HTML 속성이 명시된 요소. 현재 `VNode`에 별도의 최상위 `key` 필드가 있는 것이 아니다. |
| key가 없는 요소 | 이름이 `key`인 HTML 속성이 명시되지 않은 요소. 텍스트 VNode도 key를 가지지 않는다. |
| DOM 프로퍼티 / property | 실제 DOM 객체에서 자바스크립트로 접근하는 프로퍼티. 예: `input.value`, `input.checked`, `option.selected`. HTML 속성과 구분한다. 같은 이름이 HTML 속성과 DOM 프로퍼티 양쪽에 존재할 수도 있다. |
| properties 필드 | 지정된 입력값·체크·선택 상태 등의 DOM 프로퍼티 값을 저장한 VNode의 필드. 자바스크립트 객체의 모든 필드를 통칭하는 말이 아니다. `attributes` 필드와도 구분한다. |
| 이전 / 다음 | 각각 변경 전 기준 VDOM과 목표 VDOM. 같은 내용을 담아도 서로 별개의 VNode 객체일 수 있다. |
| 상대 위치 | 각 부모의 자식 배열에서의 위치. 예: 양쪽 트리의 첫째 자식끼리 비교. |
| 대응 | 이전 VNode 중 어떤 노드를 다음 VNode와 비교할 대상으로 삼는지 정하는 것. 실제 DOM 참조 연결과 다르다. |
| 명령 / operation | Patch가 실행할 `DiffCommand`. `insert`, `remove`, `replace`, `update`, `move` 중 하나다. |
| 순서가 있는 명령 배열 | Patch가 배열 순서대로 실행하면 목표 DOM을 만들 수 있는 명령 배열. 별도 정렬 함수를 반드시 거쳐야 한다는 뜻은 아니다. |
| dom | VNode·VRoot가 가진 실제 DOM 객체 참조. `key`가 아니며 Diff의 비교 기준도 아니다. |
| 현재 노드 비교 종료 | 해당 노드의 비교에서 돌아간다는 뜻. 부모의 나머지 자식이나 형제 순회까지 중단한다는 뜻이 아니다. |

### key의 정확한 위치

용어를 단독으로 “속성” 또는 “키”라고만 부르지 않는다. VNode 객체의 항목은 **필드**, HTML에 명시된 항목은 **HTML 속성**, 실제 DOM 객체의 항목은 **DOM 프로퍼티**로 구분한다.

```ts
vnode.tagName       // VNode의 tagName 필드
vnode.attributes    // VNode의 attributes 필드: HTML 속성 목록
vnode.properties    // VNode의 properties 필드: 지정된 DOM 프로퍼티 값 모음
input.checked       // 실제 DOM의 checked 프로퍼티
```

예를 들어 `attributes` 자체는 VNode의 필드지만, 그 배열 안의 `{ name: 'key', value: 'a' }`는 HTML의 key 속성을 표현한 데이터다.

### attribute와 property의 구분

- **HTML 속성(attribute):** HTML에 명시되거나 실제 DOM의 `getAttribute()`로 읽는 이름·값. VNode의 `attributes` 필드에 저장한다.
- **DOM 프로퍼티(property):** 실제 DOM 객체에서 `객체.이름`으로 접근하는 값. 수집 대상으로 지정된 값만 VNode의 `properties` 필드에 저장한다.
- 브라우저가 제공하는지 여부만으로 구분하지 않는다. 같은 이름이 양쪽에 존재할 수 있다.
- 예: `<option selected>`의 `getAttribute('selected')`는 HTML 속성이고 `option.selected`는 현재 선택 상태인 DOM 프로퍼티다. 현재 선택이 바뀌어도 HTML 속성이 함께 바뀌는 것은 아니다.
- 이 프로젝트의 `key`는 HTML 속성으로 읽는다. 일반 HTML 요소의 표준 DOM 프로퍼티인 `element.key`를 읽는 방식이 아니다.
- 자바스크립트 객체의 프로퍼티 키는 일반적인 필드 이름을 뜻하며, HTML의 `key` 속성이나 노드 식별자만을 뜻하지 않는다.

### HTML의 key 속성 예시

```html
<li key="a" class="item">A</li>
```

이 요소 VNode의 관련 데이터는 다음과 같다.

```ts
tagName: 'LI',
attributes: [
  { name: 'key', value: 'a' },
  { name: 'class', value: 'item' }
]
```

- `key`는 HTML 속성 이름이고, 식별에 사용하는 값은 `'a'`다.
- `tagName`, `id`, 자식 배열의 인덱스, VNode 객체 참조를 key라고 부르지 않는다.
- 일반적인 객체의 필드 이름을 뜻하는 “키”와 구분한다.
- 기존 공용 계약대로 `key` 속성은 VDOM의 `attributes`에서 제거하지 않고 실제 DOM에도 렌더링한다.
- 중복 key의 대체 대응 규칙과 비교 순서는 용어 정의만으로 확정하지 않는다.

## 2. 담당 범위와 산출물

**[공용 계약]** Diff는 이전·다음 VDOM으로부터 정렬된 변경 명령 배열을 계산한다.

```ts
diff(prevRoot: VRoot, nextRoot: VRoot): DiffCommand[];
orderChanges(changes: DiffCommand[]): DiffCommand[];
```

- 포함: 노드 대응, 종류·태그·텍스트·속성·프로퍼티 비교, 자식 재귀, 삽입·제거·이동 판단, 명령 의존 순서.
- 제외: HTML 파싱, 실제 DOM 변경·생성, 이력 저장·복원. 유지 노드의 참조 연결은 P1-PATCH-LINK-02에 따라 Diff가 담당한다.
- 변경 없음은 `[]`이다. 변경 없는 노드에 별도 명령을 만드는 계약은 없다.
- 이전 VDOM·실제 DOM·다음 VDOM의 비교용 데이터는 수정하지 않는다. 다음 VDOM의 `dom` 필드 연결만 허용한다.
- Diff 종료 시 다음 `VRoot`와 유지·이동·수정 노드의 `dom`은 이전 실제 DOM 참조를 가진다. 삽입·교체할 노드와 그 하위 트리는 `null`로 유지한다. 정렬 함수는 연결을 변경하지 않는다.
- 임시 DOM 객체의 동일성이나 `dom` 참조가 아니라 VDOM 데이터와 대응 규칙으로 비교한다.

### 입력 데이터

**[공용 계약]** `VRoot`는 `childNodes`, `dom`만 가진다. 컨테이너 자체의 태그·속성은 비교하지 않는다.

`VNode`는 `nodeType`, `tagName`, `attributes`, `nodeValue`, `childNodes`, `properties`, `dom`을 가진다. 요소는 `nodeType: 1`, 텍스트는 `3`이며 주석은 생성 단계에서 제외된다. 요소의 `tagName`은 대문자다.

- `attributes`: `{ name: string; value: string }[]`. `key`도 포함한다.
- `properties`: `Record<string, unknown>`. 입력값·체크·선택 상태를 속성과 별도로 비교한다.
- `dom`: 비교 대상 데이터가 아니라 Patch가 사용하는 실제 DOM 참조다.

### 출력 명령

**[공용 계약]** 현재 `src/vdom/types.ts`의 형태를 그대로 적는다. `parent`의 VRoot 반영은 §6과 공용 결정 `P1-VDOM-PARENT-01`을 따른다.

```ts
type UpdateData = {
  nodeValue?: string;
  setAttributes?: VNodeAttribute[];
  removeAttributes?: string[];
  setProperties?: VNodeProperties;
  removeProperties?: string[];
};

type DiffCommand =
  | { type: 'replace'; target: VNode; node: VNode }
  | { type: 'update'; target: VNode; data: UpdateData }
  | { type: 'insert'; node: VNode; parent: VNode | VRoot; before: VNode | null }
  | { type: 'remove'; target: VNode }
  | { type: 'move'; target: VNode; parent: VNode | VRoot; before: VNode | null };
```

- `target`은 이전 VDOM 객체다.
- `node`, `parent`, `before`는 다음 VDOM 객체다. 문자열·경로가 아닌 객체 직접 참조다.
- `before === null`은 맨 뒤다. `before.dom === null`을 맨 뒤로 해석하면 안 된다.
- `replace`는 제자리 교체이고 위치 변경은 `move`의 역할이다.

## 3. 노드 대응과 변경 판단을 분리한다

**[공용 계약]** 같은 부모 안에서 key가 있는 요소는 같은 key로, key 없는 요소와 텍스트는 자식 순서로 대응한다. key 없는 순서 변경을 `move`로 식별한다고 보장하지 않는다.

서로 다른 두 질문을 섞지 않는다.

1. **대응:** 이전의 어떤 노드와 다음 노드를 비교할 것인가?
2. **변경:** 대응된 노드의 실제 DOM을 유지할 수 있는가? 무엇을 바꿀 것인가?

### 3.1 key 값 변경

**[찬의 방향]** key가 바뀌었다면 같은 대상으로 판단할 수 없으며 다른 대상으로 본다.

```html
<!-- 이전 --> <li key="a">A</li>
<!-- 다음 --> <li key="b">A</li>
```

**[AI 해석]** 이 단독 사례에서는 이전 a 제거와 새 b 삽입으로 이어진다. a와 b를 대응시킨 뒤 key 속성만 update하는 흐름이 아니다. 형제가 더 있다면 각 key의 대응을 전체 형제 안에서 먼저 확인해야 한다.

**공용 문서와의 차이:** 공용 `CONF-03`에서는 key 변경 정책이 아직 미확정이다. 위 방향을 공용 계약으로 취급하지 않는다.

### 3.2 key와 태그 비교 순서

**[찬의 방향]** key와 태그 등을 어떤 순서로 확인하는지의 문제로 접근한다.

**[찬이 동의한 개인 작업 기준]** key로 대응 대상을 찾은 뒤, 종류·태그를 비교해 재사용 또는 교체를 판단한다.

```text
같은 key를 가진 이전 노드 탐색
├─ 없음 → 새 노드
└─ 있음 → 종류·태그 비교
   ├─ 같음 → 텍스트·속성·프로퍼티·자식 비교
   └─ 다름 → replace, 교체 하위 트리의 중복 명령 생략
```

예를 들어 `div key="a"` → `p key="a"`는 이 개인 기준에서 대응 후 교체다. **같은 대상으로 대응되는 것과 같은 실제 DOM 객체를 유지하는 것은 다르다.**

**[공용 계약과 구분]** 이후 단계별 논의에서 찬이 이 처리에 동의했다. 개인 작업 기준을 공용 합의로 승격하지 않으며, 공용 `CONF-03`은 유지한다.

### 3.3 중복 key 충돌

**[찬의 방향]** 중복 key는 정의되지 않은 동작 영역의 식별자 충돌로 보고, 오류로 중단하기보다 update 등의 대체 처리로 진행한다.

**[AI 해석]** 대체 처리는 먼저 대응 대상을 결정해야 한다. 대응 후 텍스트·속성만 다르면 update, 종류·태그가 다르면 replace, 개수가 다르면 insert·remove가 필요할 수 있다. 따라서 무조건 update 명령을 만드는 뜻으로 해석하지 않는다.

**[찬이 동의한 개인 작업 기준]** 같은 부모의 이전·다음 자식 목록 각각에서 중복을 확인한다. 어느 한쪽에서 중복된 key 값은 해당 비교의 양쪽 목록에서 식별자로 사용하지 않는다.

- 중복 key는 짝 찾기용 조회표에서 제외한다. 원본 VNode의 `attributes`에서 key 속성을 삭제하지 않는다.
- 무효화한 key 값은 별도로 기억한다. 단순한 조회 실패와 중복으로 인한 무효화를 구분해야 한다.
- 해당 노드들은 원래 key 없는 노드와 함께 각 목록의 출현 순서로 짝짓는다. 다른 고유 key의 대응은 유지한다.
- 중복이 아닌 key가 조회되지 않는다면 새 자식이다. 모든 조회 실패를 순서 대응으로 바꾸지 않는다. 예를 들어 이전 key a와 다음 key b는 별개 대상이다.
- 같은 값의 key가 세 번 이상 나와도 다시 유효한 key로 등록하지 않는다.
- 중복 탐지는 현재 부모의 형제 목록에서만 수행한다. 전역 트리 정보를 요구하지 않는다.

이 절은 개인 작업 기준이다. 공용 `CONF-03`이나 기존 테스트 기대 결과를 변경하지 않는다. 중복 확인과 짝 찾기 구현·검증은 §13에 기록한다.

### 3.4 key 없는 자식의 순서 — 개인 작업 기준 확정

**[찬이 선택한 방향]** key가 있는 자식과 없는 자식이 섞이면, key 없는 자식끼리의 출현 순서로 짝짓는다. 전체 자식 배열의 같은 인덱스만을 기준으로 삼지 않는다.

```text
이전: [key="a"인 LI, key 없는 P]
다음: [key 없는 P, key="a"인 LI]

LI는 key="a"로 짝짓는다.
P는 양쪽의 첫 번째 key 없는 자식이므로 짝짓는다.
```

key 없는 자식이 여러 개라면 그 자식들끼리 첫째·둘째 순서로 비교한다. 내용이나 태그를 검색해 다른 순서의 짝을 찾는 규칙이 아니다. 중복으로 식별이 무효화된 key 노드도 §3.3에 따라 이 순서 대응 대상에 포함한다. 이 절은 개인 Diff 작업 기준이며, 공용 테스트의 기대 결과나 팀 계약을 변경하지 않는다. 이동 판단은 별도다.

## 4. 함수 흐름과 명령 정렬

**[공용 계약]** 아래 내부 함수명은 공용 흐름 문서의 설명이다. 보조 함수의 인자·반환형·분담까지 확정된 것은 아니다. 개인 코드의 현재 함수명과 구조는 §9를 따른다. 아래는 공용 문서의 흐름을 인용한 것이므로 개인 코드의 이름으로 바꾸지 않는다.

```text
diff(prevRoot, nextRoot)
├─ nextRoot.dom = prevRoot.dom
├─ 루트의 자식 대응·비교
├─ compareNode(prev, next)
│  ├─ 종류·태그 변경 → replace
│  ├─ 같은 종류·태그 → linkNode(prev, next), 변경 없는 노드도 연결
│  ├─ 텍스트 변경 → update
│  ├─ diffAttributes() → 추가·변경·삭제 데이터
│  ├─ diffProperties() → 변경된 입력·선택 상태
│  └─ diffChildren()
│     ├─ 노드 대응 계산
│     ├─ 새 노드 → insert
│     ├─ 사라진 노드 → remove
│     ├─ 식별된 기존 형제 순서 변경 → move
│     └─ 대응 자식 → compareNode() 재귀
└─ orderChanges() → 적용 가능한 순서의 명령 배열
```

- 속성은 이름·값으로 비교하며 나열 순서는 무시한다. 새로운 일반 속성에 전용 분기를 추가하지 않는다.
- 프로퍼티의 `false`, 빈 문자열 변경을 누락하지 않는다.
- 실제 텍스트 노드가 바뀌는 공백 변경을 무조건 동일하다고 보지 않는다.
- 부모·기준 형제가 존재한 뒤 해당 노드를 사용하는 명령이 실행되어야 한다.
- 제거된 노드를 이후 삽입·이동의 기준으로 사용하지 않는다.
- 부모 제거·교체에 포함된 하위 트리에 중복 명령을 생성하지 않는다.
- 새 하위 트리 전체 렌더링과 개별 자식 삽입을 중복 적용하지 않는다.
- 전체 경우에서 유일한 명령 순서나 전역 최소 명령 개수를 요구하는 계약은 아니다. 개별 테스트가 지정한 결과는 그대로 따른다.

## 5. 변경 없는 노드의 참조 연결도 Diff가 담당한다

**[찬이 승인한 변경·P1-PATCH-LINK-02]** 이전의 Patch 담당 경계를 대체한다. Diff는 변경 명령을 만들기 위해 찾은 대응을 그대로 이용해 유지·이동·수정 노드에 `prev.dom`을 연결한다. 변경 없는 노드의 연결을 위해 별도 명령이나 대응 정보 반환을 추가하지 않는다.

**[공용 계약]** Diff는 `VRoot`를 연결하고, 종류·태그가 같은 대응 노드를 연결한 뒤 자식도 재귀한다. 삽입·교체할 노드와 그 하위 트리는 연결하지 않는다. Patch는 새 실제 DOM 생성과 연결을 담당하며 성공 후 다음 VDOM 전체가 연결된다.

```html
<!-- 이전 --> <div><p>A</p><span>유지</span></div>
<!-- 다음 --> <div><p>B</p><span>유지</span></div>
```

이 예시에서 변경 명령은 텍스트 A → B update면 충분하다. 다음 VDOM의 div·p·span·텍스트는 별도 객체이므로 Diff가 모두 이전 실제 DOM 참조를 연결한다. 실제 DOM의 텍스트 변경은 Patch까지 수행하지 않는다.

개인 코드에서는 `findChildMatches()`의 결과를 `collectNodeChanges()`에 전달해 `linkNode()`를 호출한다. Patch에서 전체 매칭을 다시 실행하거나 개인 짝 찾기를 다른 공유 구조로 옮기지 않는다. `DiffCommand[]` 반환과 기존 key/keyless 대응 규칙은 유지한다.

## 6. 별도로 남은 경계 계약

### 6.1 최상위 부모 타입 — 동기화 완료

**[이전 코드의 불일치]** 최상위 자식의 부모는 `VRoot`인데 `insert`·`move`의 `parent`가 `VNode`만 허용했다. 빈 루트에 첫 노드를 삽입하는 `ORDER-02`에서 드러나는 문제였다.

**[찬의 지적]** 합의 이후 `VRoot`를 도입하면서 기존 부모 타입에 반영하지 못했을 가능성이 있다. 새로운 루트 표현을 선택하는 설계 문제와 구분한다.

**[찬이 승인한 문서 분류]** 이 항목은 새 설계 미확정이 아니라 **VRoot 도입에 따른 계약 동기화 누락 추정**으로 기록한다. 누락 경위가 확인된 것은 아니다.

**[승인 후 반영]** 사용자가 부모 타입과 관련 공용 문서의 동기화를 승인해 `parent: VNode | VRoot`를 코드와 공용 문서에 반영했다. 근거는 `P1-VDOM-PARENT-01`이다. 새 루트 표현을 고안하거나 루트를 가짜 `VNode`로 바꾸지 않는다. Patch 구현은 수행하지 않았다.

### 6.2 replace·move 의미 — 추가 협의 사항 아님

**[찬의 확인]** Patch는 Diff 명령대로 실행한다. `replace`는 대상을 새 노드로 교체하고, `move`는 동적 배열에서 원소를 옮기듯 대상을 지정 위치로 이동한다. 이는 기존 명령의 의미와 인터페이스 계약에 따른 것이며, 별도 설계 선택으로 다시 묻지 않는다.

**[공용 테스트]** `ORDER-05`는 A를 A'로 교체한 뒤 A'를 이동시키는 동작을 요구한다.

```text
시작:    A(div) → B → C
교체:    A'(p)  → B → C
이동:    B      → A'(p) → C
```

Diff는 replace와 move의 역할을 섞지 않고, 지정 대상과 위치 및 실행 순서를 명령으로 표현한다. 기존 `target`·`node`·`parent`·`before`의 참조 방향은 §2의 공용 계약을 따른다.

이전 AI 설명은 Patch의 내부 참조 처리 우려를 별도의 계약 미확정 사항으로 확대했다. 해당 분류를 철회한다. Patch 내부의 참조 처리 방식은 이 Diff 문서에서 정하지 않는다.

## 8. AI 작업 통제 기준

- 찬이 소유할 판단: 대응 규칙, 명령의 예상 결과, 불변 조건, 경계 계약 승인.
- AI에 맡길 작업: 승인된 판단을 코드로 표현, 기존 명세에 따른 테스트 작성·실행, 결과 보고.
- 구현 전에는 해당 범위의 예상 명령을 예시로 확인한다.
- 한 번에 하나의 판단 범위만 구현하고 관련 없는 규칙을 바꾸지 않는다.
- 미확정 사항에 의존하면 멈추고 확인한다. 개인 방향을 팀 합의로 승격하지 않는다.
- 기존 테스트의 기대 결과를 구현에 맞춰 수정하지 않는다.
- 완료 보고에는 변경 함수, 기존 테스트 ID, 실제 실행 결과, 추가로 선택한 사항과 이유·영향 범위를 남긴다.

### 이 문서 작성의 선택 기록

- 선택: 기존 공용 문서를 수정하지 않고 `docs/p1_diff_notes.md`에 개인 작업 내용을 분리했다.
- 이유: 찬의 요청대로 개인 판단·AI 제안과 팀 합의를 섞지 않기 위해서다.
- 영향 범위: 이 파일만 추가한다. 공용 타입·함수·테스트·결정 상태는 변경하지 않는다.

## 9. 논의 후 작성한 함수 뼈대

**[찬이 요청한 작업]** 논의한 함수의 입력·출력·책임을 실제 TypeScript 코드로 표현한다. 처음에는 `src/vdom/diff.ts`에 두었고, 이후 §12에서 [src/vdom/diff/](../src/vdom/diff/)로 분리했다. 외부 진입점은 [index.ts](../src/vdom/diff/index.ts)다.

```text
diff → collectChildChanges → findChildMatches
                           → collectNodeChanges → collectChildChanges (재귀)
                                                → findAttributeUpdates
                                                → findPropertyUpdates
                           → collectMoveChanges
     → orderChanges
```

- 초기에는 `diff()`만 자식 비교와 최종 정렬 호출을 연결했다. 이후 §11에서 `collectChildChanges()`, §13에서 `findChildMatches()`, §14에서 노드 연결·취합, §16에서 속성 비교, §17에서 프로퍼티 비교, §19에서 이동 판단을 작성했다. 정렬은 미구현 오류를 던진다.
- `Parent`, `ChildMatch`, `AttributeUpdate`는 현재 `src/vdom/diff/types.ts`에 둔다. `AttributeUpdate`는 내부 타입이며 작업이 없는 필드를 생략한다. 변경이 없으면 빈 객체다.
- 자식 대응·이동 선택·명령 정렬 알고리즘은 구현하지 않는다.
- 미구현 함수를 빈 배열 반환으로 대체하지 않는다. 변경 없음으로 오인하는 것을 막기 위한 선택이다.
- 사용되지 않는 매개변수에는 `_` 접두사를 붙여 기존 TypeScript의 미사용 매개변수 검사를 통과하도록 한다.
- 뼈대 작성 당시에는 공용 타입을 변경하지 않았다. 이후 §11에서 승인된 부모 타입 동기화를 반영했다. 기존 테스트 기대 결과는 변경하지 않는다.
- 별도 정렬 함수가 필수라는 일반 결론이 아니라, 이번에 논의한 함수 구조를 코드로 확인하기 위한 뼈대다.

### 함수 이름 규칙

**[찬이 요청한 정리]** 이름만으로 처리 대상과 반환 결과를 알 수 있도록 아래 규칙을 적용한다. 기존 공용 문서의 이름을 변경하는 것은 아니다.

- `collect…Changes`: 해당 범위에서 필요한 **DiffCommand 배열**을 모아 반환한다. 단순한 참·거짓 비교 함수가 아니다.
- `find…Matches`: 비교할 **VNode 짝과 새·사라진 노드의 분류**를 찾아 반환한다. 변경 명령을 반환하지 않는다.
- `find…Updates`: update 명령에 넣을 **변경 데이터**를 찾아 반환한다. DiffCommand 배열이 아니다.
- `orderChanges`: 받은 변경 명령의 실행 순서를 정한다. 공용 계약의 이름을 유지한다.
- `diff`: 외부 진입점의 공용 계약 이름을 유지한다.
- `Child`, `Node`, `Move`, `Attribute`, `Property`로 책임 범위를 드러낸다. `compare`처럼 결과가 참·거짓인지 변경 데이터인지 알기 어려운 이름은 내부 함수에서 사용하지 않는다.

| 이전 개인 코드 이름 | 현재 이름 | 반환 결과 |
| --- | --- | --- |
| compareChildren | collectChildChanges | 직계 자식과 하위 트리의 DiffCommand[] |
| matchChildren | findChildMatches | ChildMatch[] |
| compareNode | collectNodeChanges | 노드 자체와 하위 트리의 DiffCommand[] |
| planMoves | collectMoveChanges | move 명령 배열 |
| diffAttributes | findAttributeUpdates | 설정할 HTML 속성과 제거할 속성 이름 |
| diffProperties | findPropertyUpdates | update.data의 설정·제거 프로퍼티 항목 |

선택 이유는 입력·출력·책임을 이름에 드러내기 위해서다. 영향 범위는 개인 함수 뼈대와 이 문서이며, 함수의 입력·출력 타입과 미구현 상태, 공용 계약과 기존 테스트는 변경하지 않는다.

## 10. 공용 Diff 테스트 명세의 코드화

**[찬이 승인한 작업 범위]** `DIFF-01`–`DIFF-09`, `ORDER-01`–`ORDER-05`에서 Diff·정렬 종료 시점의 검증을 Vitest·jsdom으로 작성한다. Patch 적용 후 결과는 보류 항목으로 구분한다. 구현·공용 타입·기존 기대 결과는 변경하지 않는다.

### 작성 내용과 선택 기록

- 파일: [tests/unit/diff/vdom.diff.test.ts](../tests/unit/diff/vdom.diff.test.ts).
- `diff()` 결과와 명세에 있는 `orderChanges()`의 정렬 결과를 호출해 검증한다. 현재 외부 진입점은 diff만 노출하고, 정렬 테스트는 orderChanges 파일에서 직접 가져온다. 그 밖의 내부 함수 호출 구조는 이 테스트로 강제하지 않는다.
- `DIFF-03`은 실제 속성 변경과 나열 순서만 바뀐 경우를 나눈다. 속성 변경을 하나의 update로 합칠지 나눌지는 강제하지 않는다.
- `DIFF-05`는 value A→B, value A→빈 문자열, checked true→false, OPTION selected false→true로 나눈다.

- 공통 검증으로 이전·다음 VDOM의 데이터·배열·객체 참조 및 실제 DOM의 데이터·노드 동일성을 확인한다. 작성 당시에는 다음 `VRoot`·모든 `VNode`의 `dom`도 null로 유지하도록 확인했다. 이 조건은 P1-PATCH-LINK-02로 대체했으며 §14에서 다음 VDOM의 `dom` 연결만 허용하도록 검증을 동기화했다.
- 생성 함수가 미구현이어도 Diff 테스트를 준비할 수 있도록 테스트 내부에서 HTML을 파싱해 독립 입력을 구성한다. 이는 테스트 준비용 코드이며 생성 함수의 구현·검증을 대신하지 않는다.
- `ORDER-02`는 명세가 허용한 별도 자식 삽입 계획도 배제하지 않고 부모 선행·동일 노드 명령 중복을 확인한다. 실제 하위 DOM 중복 생성 여부는 Patch 적용 후 검증으로 남긴다.

## 11. collectChildChanges 취합 로직 작성

**[찬이 요청·승인한 범위]** `collectChildChanges()`를 작성하고, 명령의 부모 타입과 관련 공용 문서를 동기화한다. 짝 찾기·개별 노드 비교·이동 판단·정렬의 내부 알고리즘은 구현하지 않는다.

### 동작과 선택 기록

- 양쪽 직계 자식이 모두 비어 있으면 `[]`를 반환한다.
- `findChildMatches()`에서 받은 새 자식은 insert, 사라진 자식은 remove 명령으로 만든다. 삽입·제거 하위 트리에 별도로 내려가지 않는다.
- 대응된 자식은 `collectNodeChanges()`의 반환 명령을 모은다. 그 함수가 자식 비교를 다시 호출하면 하위 명령도 취합되는 구조다. 이 절 작성 당시 해당 함수는 미구현이었으며 이후 §14에서 연결·취합 흐름을 작성했다.
- `collectMoveChanges()`의 반환 명령을 마지막에 취합한다. 이것은 최종 실행 순서가 아니다. `orderChanges()`의 책임은 유지한다.
- 삽입의 `before`는 다음 목록의 바로 오른쪽 VNode, 마지막이면 null로 지정한다. `ORDER-01`처럼 새 기준 형제의 생성 의존성은 최종 정렬에서 처리한다.
- 오른쪽 형제를 찾는 표를 한 번 만들어 반복 탐색을 피한다. 이 표는 다음 VDOM 객체끼리의 관계만 저장한다. Patch를 모의 실행하거나 작업용 자식 배열을 변경하지 않는다.
- 입력 배열·VNode 비교용 데이터·이전 DOM 참조는 수정하지 않는다. 이후 §14의 변경으로 대응된 다음 VNode의 DOM 참조는 연결한다. 하위 함수의 오류를 삼키거나 변경 없음으로 바꾸지 않는다.
- `parent: VNode | VRoot` 반영은 공용 결정 `P1-VDOM-PARENT-01`을 따른다. 기존 테스트 기대 결과는 유지한다.

### 테스트와 검증 상태

- 새 테스트: `tests/unit/diff/vdom.collect-child-changes.test.ts`. 빈 자식 목록, 루트 아래 하위 트리 삽입, 연속 삽입의 기준 형제, 상위 제거의 하위 중복 방지를 검증하도록 작성했다.
- 기존 `tests/unit/diff/vdom.diff.test.ts`는 수정하지 않았다.
- 구현 전 새 테스트 4개가 모두 `collectChildChanges: 미구현`으로 실패하는 것을 확인했다.
- 작성 후 `npm run typecheck` 통과, `git diff --check` 통과.
- 전체 테스트: 2개 통과, 20개 실패, 2개 건너뜀, 5개 보류. 새 테스트 중 빈 목록은 통과하고 나머지 3개는 `findChildMatches: 미구현`으로 실패한다. 기존 실패도 `findChildMatches` 또는 `orderChanges` 미구현에서 발생한다.
- **당시 실제 하위 함수를 사용하는 취합 검증은 미완료였다.** 이후 §12에서 하위 함수의 결과를 대체한 격리 테스트로 취합 책임을 검증했다. 실제 하위 함수와의 연계 및 재귀 동작 검증은 여전히 미완료다. 테스트를 통과시키려고 하위 함수를 임의 구현하거나 기존 기대 결과를 바꾸지 않았다.

동기화한 공용 문서는 `p1_interfaces.md`, `p1_function_flow.md`, `p1_prd.md`, `p1_test_cases.md`, `p1_decisions.md`다. 변경은 승인된 부모 타입 반영으로 한정한다.

## 12. 함수별 파일 분리와 collectChildChanges 격리 검증

**[찬이 선택한 작업]** 함수의 인자에 테스트용 의존성을 추가하는 대신 `diff/` 폴더 안에서 파일을 분리하고, 하위 함수 모듈을 대체해 취합 책임을 검증한다. 함수의 입력·출력·동작은 변경하지 않는다.

### 파일 구조와 선택 기록

```text
src/vdom/diff/
├─ index.ts
├─ diff.ts
├─ collectChildChanges.ts
├─ findChildMatches.ts
├─ collectNodeChanges.ts
├─ collectMoveChanges.ts
├─ findAttributeUpdates.ts
├─ findPropertyUpdates.ts
├─ orderChanges.ts
└─ types.ts
```

- 기존 `src/vdom/diff.ts`를 위 구조로 이동했다. 처음에는 index에서 모두 다시 내보냈지만, 이후 찬의 지적에 따라 **현재 `index.ts`는 diff만 내보낸다.** `.../vdom/diff`는 외부 진입점이며 세부 함수·내부 타입은 개별 파일에서 가져온다.
- 내부 호출은 `index.ts`를 거치지 않고 개별 함수 파일에서 직접 가져온다. 테스트에서 해당 모듈을 대체할 수 있고, 내부 의존성이 진입점에 되돌아가지 않도록 하기 위한 선택이다.
- 공통 VDOM·명령 타입은 기존 `src/vdom/types.ts`를 유지한다. Diff 내부 타입만 `diff/types.ts`에 둔다.
- `collectChildChanges()`의 취합 로직을 그대로 옮겼다. 테스트 편의를 위한 함수 인자·주입 객체·공유 상태는 추가하지 않았다.
- 파일 분리 당시에는 짝 찾기·노드 변경·이동·속성·프로퍼티·정렬 함수가 미구현이었다. 이후 §13에서 짝 찾기, §14에서 노드 연결·취합 흐름을 작성했다.
- 공용 인터페이스 문서는 새 외부 진입점과 내부 계약의 위치를 구분한다. 파일 분리 직후에는 기존 테스트를 그대로 두었고, 이후 공개 범위를 diff로 제한하면서 기존 테스트 두 파일의 세부 함수 가져오기 경로만 바꿨다. 공용 테스트 명세와 기대 결과는 바꾸지 않았다.

### 격리 테스트의 범위

파일: [tests/unit/diff/vdom.collect-child-changes.isolated.test.ts](../tests/unit/diff/vdom.collect-child-changes.isolated.test.ts).

실제 `collectChildChanges()`를 실행하고 `findChildMatches`, `collectNodeChanges`, `collectMoveChanges` 모듈만 가짜 결과로 대체한다. 가짜 함수 자체의 정답 여부가 아니라 취합 함수의 실제 반환값·객체 참조·인자 전달·오류 전달을 검증한다.

- 빈 목록에서 불필요한 하위 호출 생략.
- 부모의 실제 직계 자식 배열을 짝 찾기에 전달.
- 새 하위 트리의 단일 삽입과 루트 부모 참조.
- 결과 배열 순서가 달라도 다음 자식 배열을 기준으로 before 지정.
- 상위 제거의 하위 중복 명령 방지.
- 짝별 정확한 인자 전달과 여러 명령·빈 결과의 취합.
- 삽입·제거·노드 변경·이동의 혼합 결과 취합과 입력·하위 반환 배열 보존.
- 하위 세 함수 각각의 오류를 동일한 오류 객체로 전달하고 후속 처리 중단.

이는 실제 짝 찾기·이동 계획의 정확성이나 실제 재귀 호출·최종 실행 순서를 증명하지 않는다. 그 범위는 기존 실제 함수 기반 테스트에 남긴다.

### 실행 결과

- 분리 전 새 테스트는 대상 모듈 파일이 없어 가져오기 단계에서 실패했다. 동작 검증이 실행된 실패와는 구분한다.

- 찬의 지적에 따라 `index.ts`는 `diff()`만 내보낸다. 세부 함수와 내부 타입은 외부 진입점에서 제외한다.

- `tests/unit/diff/vdom.diff-entry.test.ts`는 외부 진입점의 실행 시 내보내기가 diff 하나뿐인지 검증한다. 변경 전 세부 함수가 함께 노출되어 실패하는 것을 확인했다.
- 변경 후 외부 진입점 테스트 1개와 취합 격리 테스트 10개, 총 **11개 통과**. 타입 검사와 `git diff --check`도 통과했다. 이 확인만으로 기존 실제 하위 함수 기반 테스트의 실패가 해결됐다고 보고하지 않는다.

## 13. findChildMatches 구현 — 같은 파일의 비공개 보조 함수

**[찬이 요청한 범위]** `findChildMatches()`의 단계를 함수로 나누되 보조 함수는 같은 파일 안에 두고, 보조 함수 자체는 별도 검증 대상으로 삼지 않는다.

파일: [src/vdom/diff/findChildMatches.ts](../src/vdom/diff/findChildMatches.ts).

```text
findChildMatches(prevChildren, nextChildren)
├─ findDuplicateKeys()       → 양쪽에서 식별자로 쓰지 않을 key 집합
├─ indexPreviousChildren()   → 고유 key 조회표 + 순서 대응 목록
├─ matchNextChildren()       → 다음 순서의 짝·새 자식 + 사용한 이전 노드 집합
└─ findRemovedMatches()      → 남은 이전 자식 분류를 이전 순서로 추가
```

- 위 보조 함수들과 HTML key 속성을 읽는 `readKey()`는 export하지 않는다. 외부 진입점의 노출 범위는 기존대로 diff 하나다.
- 보조 함수는 직접 호출하거나 가짜 함수로 대체하여 테스트하지 않는다. 실제 `findChildMatches()`의 반환 결과로 검증한다.
- 중복 집합은 이전·다음 목록에서 각각 중복 여부를 확인한 뒤 합친다. 이전·다음에 동일한 key가 하나씩 있는 정상 매칭을 중복으로 오인하지 않는다.
- 한쪽에서 중복된 key 값은 양쪽에서 순서 대응으로 처리한다. 무효화된 노드와 원래 key 없는 노드를 각 목록의 출현 순서로 함께 짝짓는다. 따라서 무효화된 서로 다른 key 값 사이에서도 순서에 따라 짝이 생길 수 있다. 이는 고유 key 변경을 순서 대응하는 것과 다르다.
- 고유 key의 조회 실패는 inserted다. 이전의 key 없는 노드로 대체하지 않는다. 명시된 빈 문자열 key도 고유 key로 사용할 수 있다.
- 모든 저장소는 호출 내부 지역 값이다. 다음 호출이나 다른 부모에 이전 key 정보를 남기지 않는다. 자식 아래로 재귀 탐색하지 않는다.
- 입력 배열·속성·프로퍼티·하위 데이터·DOM 참조는 변경하지 않는다. 순서 대응은 `unkeyedChildren.values()`의 반복자로 다음 이전 노드를 하나씩 읽는다. 사용자가 승인한 정리로 수동 인덱스 증가를 제거했으며, keyed 조회에서는 반복자를 소비하지 않는다. 대응 규칙과 반환 결과는 유지한다.
- 기존 타입·명령 취합 로직·노드 비교·이동 판단·정렬·공용 테스트 기대 결과는 변경하지 않는다. 공용 CONF-03은 그대로 두고 개인 방향의 검증을 별도 테스트 파일에 둔다.

## 14. Diff의 DOM 연결 — 탑다운 흐름 유지

**[찬이 요청·승인한 변경]** P1-PATCH-LINK-02를 개인 Diff 코드에 적용한다. 루트와 유지·이동·수정 노드는 Diff가 연결하며, 삽입·교체 노드와 그 자손은 Patch 생성 시 연결한다. 기존 key/keyless 짝 찾기 규칙과 명령 반환 계약은 유지한다.

```text
diff
├─ nextRoot.dom = prevRoot.dom
├─ collectChildChanges
│  ├─ findChildMatches
│  ├─ 새 자식 → insert / 사라진 자식 → remove
│  ├─ collectNodeChanges
│  │  ├─ linkNode: 종류·태그 불일치 → 연결 없이 replace 후 종료
│  │  └─ 일치 → 이전 DOM 연결
│  │     ├─ 텍스트 update 또는 빈 배열
│  │     └─ 요소의 속성·프로퍼티 변경 취합 → collectChildChanges 재귀
│  └─ collectMoveChanges
└─ orderChanges
```

- `src/vdom/link.ts`는 공용 계약의 `linkNode()`만 구현했다. 전체 트리 재매칭, 별도 대응표, 새로운 식별 규칙은 추가하지 않는다. `linkMatchedDom()` 등 다른 공용 유틸리티는 이번 범위에 포함하지 않는다.
- 이 작업 당시 `collectNodeChanges()`는 교체·텍스트 변경과 요소의 하위 결과 취합·재귀를 수행했고, `findAttributeUpdates()`, `findPropertyUpdates()`, `collectMoveChanges()`, `orderChanges()`는 미구현이었다. 이후 속성 비교 구현은 §16을 따른다.
- 변경 없는 노드와 자손도 연결한다. 삽입 지점 이후 노드는 실제 DOM의 현재 인덱스가 아니라 기존 `findChildMatches()`가 찾은 짝의 DOM을 이어받는다. key 없는 노드는 기존 순서 대응이며 중간 삽입의 객체 유지가 보장되지 않는다.
- 이전 VDOM이 실제 DOM에 연결되어 있다는 전제를 유지한다. 누락된 이전 참조의 오류 처리나 Diff 실패 시 부분 연결된 다음 VDOM의 폐기 정책은 새로 확정하지 않는다.

## 16. HTML 속성 변경 계산

- **사용자가 승인한 범위:** `findAttributeUpdates()`만 구현한다. 속성명 기준 추가·변경·삭제를 찾고, 순서 변경은 무시하며, 변경이 없으면 `{}`를 반환한다. 프로퍼티 비교·이동·정렬·Patch는 구현하지 않는다.
- **선택과 이유:** 기존 HTML 속성 목록을 이름별 `Map`으로 조회해 다음 목록에서 추가·변경, 이전 목록에서 삭제를 찾는다. 속성마다 반대편 배열 전체를 반복 탐색하지 않으며, 기존 `AttributeUpdate`를 재사용한다. 입력 목록과 속성 객체는 변경하지 않는다.
- **시험:** 공용 DIFF-03의 두 입력과 기대 결과를 `tests/unit/diff/vdom.find-attribute-updates.test.ts`에 함수 단위로 적용했다. 구현 전 2개 모두 미구현 오류로 실패했고, 구현 후 2개 통과했다. 기존 DIFF-03의 전체 `diff()` 테스트를 대체하거나 기대 결과를 바꾸지 않는다.
- **검증:** 타입 검사와 `git diff --check` 통과. 전체 테스트 40개 통과, 20개 실패, 2개 건너뜀, 5개 보류. 실패는 `findPropertyUpdates`, `collectMoveChanges`, `orderChanges` 미구현이며, 전체 `diff()` 및 Patch 완료를 의미하지 않는다.

## 17. DOM 프로퍼티 변경 계산

- **사용자가 승인한 범위:** `findPropertyUpdates()`에서 추가·변경은 `setProperties`, 사라진 이름은 `removeProperties`로 계산한다. 값이 같으면 생략하고 입력 객체와 실제 DOM을 수정하지 않는다.
- **값 범위:** 문서상 현재 수집 대상은 문자열과 불리언이다. 같은 이름의 값은 엄격 부등 비교한다. `VNodeProperties`는 여전히 `unknown`이며 Snapshot 생성은 미구현이므로 타입이 원시값만 보장한다고 주장하지 않는다. 참조형 값의 내용 비교 정책은 확정하지 않는다.
- **시험:** 기존 DIFF-05의 값 변경·false·빈 문자열과 승인된 추가·제거·혼합·변경 없음·입력 보존을 `tests/unit/diff/vdom.find-property-updates.test.ts`에 작성했다. 구현 전 8개 미구현 실패, 구현 후 8개 통과. 기존 DIFF-05와 격리 테스트의 명령 필드를 `setProperties`로 동기화했다.

- **검증 경계:** 계획의 참조 유효성과 입력·실제 DOM 보존을 확인한다. 이동만 있는 다섯 사례와 네 형제의 24개 순열은 실제 `orderChanges()`로 정렬 후 move를 표준 DOM 연산으로 적용해 목표 순서·객체 동일성을 확인한다. 제품 Patch 검증은 아니다. 이동·삽입 및 이동·삭제의 실제 Patch 연계 2개는 `it.todo`다.
- **최초 실행:** 신규 실행 테스트 41개 모두 `collectMoveChanges: 미구현`으로 실패, 2개 보류. 타입 검사 통과. 이동 계획만 구현하더라도 정렬 미구현으로 최종 순서 검증은 완료되지 않는다.

### 알고리즘 후보 — 제안, 제품 코드 미반영

1. 기존 `matches`를 재사용해 삽입·제거를 제외한 이전 형제 순서와 목표 기존 형제 순서를 준비한다. 양쪽 순서는 동일한 이전 VNode 객체로 표현해 참조로 비교할 수 있다.
2. 이전 순서의 작업용 복사본을 목표와 왼쪽부터 비교한다. 현재 위치와 목표 노드가 다르면 목표 노드를 해당 위치로 옮기고 이동 대상으로 기록한다. 실제 DOM·입력은 변경하지 않는다. 최소 이동 횟수는 보장하지 않는다.
3. 각 이동 대상은 이전 VNode를 `target`, 다음 부모를 `parent`, 전체 다음 자식 목록의 바로 오른쪽 형제를 `before`로 지정한다. 마지막은 null이다. 작업 목록에서 옮긴 위치와 실제 명령의 기준 형제를 혼동하지 않는다.
4. 정렬 단계에서 같은 부모의 삽입·이동을 목표 순서 오른쪽부터 적용하면 기준 형제가 먼저 준비된다. 새 기준 형제의 생성은 사용보다 먼저, 교체는 해당 새 노드를 사용하는 이동보다 먼저 처리해야 한다. 이 순서는 정렬 구현 논의·실제 테스트로 별도 검증해야 한다.

- **분리 후보:** 대응된 형제 순서 준비 → 작업 목록에서 이동 대상 선택 → 다음 트리 참조를 가진 명령 생성. 필요하면 같은 파일의 비공개 함수로 나눈다. 제안 단계에서 새 자료구조나 공용 API를 확정하지 않는다.
- **독립 모형 실험:** 이전 abcd에 대해 abcdx 부분집합의 모든 목표 순서 326개를 문자열 목록으로 확인했다. 제거 후 삽입·이동을 목표 오른쪽부터 적용하면 후보 계획으로 목표에 도달했다. 제품 VNode·정렬·Patch를 실행한 검증이 아니며 실제 테스트의 실패를 대신하지 않는다.

## 19. 이동 계획 하위 함수 구현

- **사용자 승인:** 1레벨 흐름에 이어 세 하위 함수를 구현한다. `orderChanges()`와 Patch는 구현하지 않는다.
- `collectMatchedChildren()`는 이미 계산된 대응 결과에서 이전 노드 참조를 다음 순서로 모으고, 대응된 노드만 이전 목록에 남겨 두 순서를 만든다. 삽입·제거로 밀린 인덱스를 이동으로 오판하지 않는다.
- `findMovedChildren()`는 이전 순서의 복사본을 목표와 왼쪽부터 맞추며 이동 대상을 기록한다. 입력은 수정하지 않고 최소 이동 횟수는 보장하지 않는다.
- `createMoveCommands()`는 기존 대응 결과로 이전 노드에서 다음 노드를 찾고, 다음 전체 형제 목록의 오른쪽 노드를 기준으로 move를 만든다. 새로운 형제는 아직 dom이 null이어도 VNode 참조를 사용한다. 최종 실행 순서는 정렬의 책임이다.
- **선택 기록:** 같은 파일의 비공개 함수와 기존 타입을 재사용했다. 대응 자료에 노드가 없거나 다음 위치가 없는 내부 불일치는 명령을 조용히 누락하지 않고 오류로 알린다. 정상 입력 계약과 기존 테스트 기대 결과는 변경하지 않는다.
- **검증:** 타입 검사와 `git diff --check` 통과. 이동 테스트 12개 통과, 29개는 `orderChanges: 미구현`으로 실패, Patch 연계 2개 보류. 전체 테스트는 63개 통과·46개 실패·2개 건너뜀·7개 보류이며 실행된 실패 원인은 정렬 미구현뿐이다.
- 이동 계획의 사례별 참조·입력 보존은 통과했지만, 24개 전체 순열과 실제 DOM 최종 순서 검증은 정렬 미구현 때문에 아직 완료되지 않았다. 테스트를 수정하거나 정렬을 대체해 통과시키지 않았다.
