# 작업 교훈

## 내부 타입은 생산자와 소비자의 실제 계약부터 확인한다

- **사례:** `AttributeUpdate`에서 변경이 없는 속성 목록도 빈 배열로 반환하도록 정해, `collectNodeChanges()`가 빈 배열을 다시 걸러내는 코드가 생겼다.
- **교훈:** 내부 반환 타입을 정하기 전에 생산자가 어떤 결과를 만들고 소비자가 어떤 형태를 실제로 필요로 하는지 함께 확인한다. 변경 없음이 유효한 결과라면 빈 배열을 강제하는 대신 필드 생략이 더 단순할 수 있다.
- **주의:** 모든 필드를 선택 항목으로 바꾸지는 않는다. `ChildMatch`처럼 분류에 따라 반드시 필요한 값은 필수로 유지해 잘못된 상태를 방지한다. 공유 타입은 내부 타입과 영향 범위를 구분한다.
- **검증:** 변경이 전혀 없을 때 불필요한 명령이 만들어지지 않는지, 일부 필드만 바뀌었을 때 해당 변경만 전달되는지, 기존 명령과 테스트 계약이 유지되는지 확인한다.

## 관찰한 결함을 정상 기대값으로 고정하지 않는다

- **사례:** 회원가입 데모의 테스트가 State·입력 DOM 불일치와 커서 끝 이동을 현재 경계로
  통과시켰다. 관찰 기록으로는 유효하지만 원하는 동작의 검증과는 구분해야 한다.
- **교훈:** State가 달라졌는지와 실제 DOM이 원하는 값과 다른지를 독립적으로 조합한다.
  같은 State라도 DOM은 다를 수 있고, State가 달라도 DOM은 이미 맞을 수 있다.
- **검증:** State 텍스트·실제 DOM·선택·쓰기 횟수를 함께 본다. 이벤트 대상 확인을 끄면
  동일 State 사례가, 커서 보정을 끄면 값 변경 사례가 실패해야 한다. 테스트 통과 수를
  명세가 없는 경로까지의 보장으로 확대하지 않는다.
- **주의:** 기존 UPD-06은 특정 연속 setter 사례다. 일반 문구만으로 모든 외부 DOM 변경의
  자동 복구가 이미 승인됐다고 해석하지 않는다. 새 경로는 사용자 합의와 명세로 명시한다.
