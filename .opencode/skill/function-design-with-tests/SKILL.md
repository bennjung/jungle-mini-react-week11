# 함수 설계와 검증을 함께 진행하기

## 1. 맥락과 위치 확인

- 작업 단계에 해당하는 `resc/phase1.md` 또는 `resc/phase2.md`를 읽는다. 두 단계를 연결하면 둘 다 읽는다.
- 현재 소스, 해당 함수의 호출자·하위 함수, 관련 `docs/` 설계·테스트·결정 문서와 기존 테스트를 확인한다. 문서상 제안과 사용자 합의를 구분한다.
- 위에서 아래로 진행한다. 함수를 바꿔 설명하기 전 호출 트리를 보여 주고 현재 위치와 작성·미구현 상태를 표시한다. 재귀와 이벤트 호출은 구분한다.

## 2. 작성된 함수 이해

- 목표, 입력, 반환, 부수 효과를 먼저 설명한다.
- 코드를 실행 순서대로 설명한다. 모든 분기·조기 반환·반복·오류 전파·상태 변경을 다루며 정상 흐름만 설명하지 않는다.
- 하위 호출은 내부 코드를 설명하지 않는 블랙박스로 취급한다. 호출에 전달하는 값, 하위 함수가 해야 할 일, 기대하는 결과와 그 결과를 사용하는 방법을 설명한다. 미구현 함수의 기대 역할과 실제 동작을 구분한다.
- 사용자가 더 깊이 보기를 원하거나 이해를 확인하기 전에는 다음 하위 함수의 내부로 자동 진행하지 않는다. 짧은 예시가 필요하면 기존 계약을 따르고 미확정 규칙을 확정된 것으로 제시하지 않는다.

## 3. 미구현 함수의 설계와 검증 논의

- 요구사항·현재 계약·확인되지 않은 사항을 나눠 설명한다. 기존 타입·함수·자료구조가 이미 역할을 수행하는지 확인하고 재사용을 우선한다.
- 내부 타입도 생산자와 소비자가 실제로 필요한 값을 기준으로 검토한다. 변경 없음이 정상인 경우 빈 값 강제나 불필요한 변환이 필요한지 확인한다. 반대로 필수값이 잘못된 상태를 막는다면 선택 항목으로 느슨하게 만들지 않는다.
- 구현 코드가 아니라 **반드시 지켜야 할 동작과 그 검증 방법을 함께** 제안한다. 각 항목에 목적, 입력·사전 상태, 기대 결과, 보존해야 할 것과 검증 시점을 적는다. 실패·경계 상황도 현재 요구 범위에서 확인한다.
- 기존 테스트 명세와 테스트의 식별자를 먼저 연결한다. 명세에 없는 기대 결과가 필요하면 근거와 영향을 설명하고 사용자에게 확인한다. 기존 기대 결과를 구현에 맞춰 임의로 바꾸지 않는다.
- 구현 대안이 필요한 경우 기존 구조로 충분한지, 무엇이 단순해지거나 어려워지는지 설명한다. 불필요한 하위 함수·타입·계층을 만들지 않는다. 설계 결정이 필요하면 선택을 사용자에게 맡긴다.
- 사용자가 내부 구현의 상세 설명을 원하지 않으면 검증 기준과 선택 이유에 집중한다. 설명 요청을 설계 승인이나 구현 승인으로 간주하지 않는다.

## 4. 승인 후 테스트와 구현

- 사용자에게 합의한 범위를 확인하고 명시적 승인 후에만 관련 테스트와 구현을 수정한다. 사용자가 지정한 테스트 범위·위치와 테스트 동결 규칙을 따른다.
- 가능한 경우 승인된 기존 테스트 또는 승인된 명세에서 도출한 테스트를 먼저 작성·실행해 변경 전 실패 원인을 확인한다. 이미 구현된 동작을 정리하거나 검증하는 경우 기존 통과 상태를 기록하고, 실패를 인위적으로 만들지 않는다.
- 최소 구현을 수행한다. 다른 미구현 함수는 요청 없이 구현하거나 빈 결과로 위장하지 않는다. 격리 테스트를 위해 하위 함수를 대체했다면 실제로 실행한 경계와 대체한 경계를 구분한다.
- 관련 테스트·타입 검사 등을 실행한다. 기존 실패와 새 실패, 건너뜀·보류, 실행하지 못한 검증을 구분한다. 단위 테스트 통과를 전체 흐름이나 실제 화면 검증 완료로 확대하지 않는다.
- 합의된 변경에 영향받는 설계·테스트·결정 기록을 함께 확인하고 필요한 문서만 동기화한다. 자율적으로 선택한 구현 방식은 이유와 영향 범위를 기록한다.
- 결과를 보고한 뒤, 사용자가 이어가기를 원할 때 다음 함수의 위치를 다시 보여 준다.
